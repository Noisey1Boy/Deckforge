   315→### Cognitive Load Assessment
   316→
   317→Cognitive load is the total mental effort required to use an interface. Overloaded users make mistakes, get frustrated, and leave. This reference helps identify and fix cognitive overload.
   318→
   319→---
   320→
   321→#### Three Types of Cognitive Load
   322→
   323→##### Intrinsic Load: The Task Itself
   324→Complexity inherent to what the user is trying to do. You can't eliminate this, but you can structure it.
   325→
   326→**Manage it by**:
   327→- Breaking complex tasks into discrete steps
   328→- Providing scaffolding (templates, defaults, examples)
   329→- Progressive disclosure: show what's needed now, hide the rest
   330→- Grouping related decisions together
   331→
   332→##### Extraneous Load: Bad Design
   333→Mental effort caused by poor design choices. **Eliminate this ruthlessly.** It's pure waste.
   334→
   335→**Common sources**:
   336→- Confusing navigation that requires mental mapping
   337→- Unclear labels that force users to guess meaning
   338→- Visual clutter competing for attention
   339→- Inconsistent patterns that prevent learning
   340→- Unnecessary steps between user intent and result
   341→
   342→##### Germane Load: Learning Effort
   343→Mental effort spent building understanding. This is *good* cognitive load; it leads to mastery.
   344→
   345→**Support it by**:
   346→- Progressive disclosure that reveals complexity gradually
   347→- Consistent patterns that reward learning
   348→- Feedback that confirms correct understanding
   349→- Onboarding that teaches through action, not walls of text
   350→
   351→---
   352→
   353→#### Cognitive Load Checklist
   354→
   355→Evaluate the interface against these 8 items:
   356→
   357→- [ ] **Single focus**: Can the user complete their primary task without distraction from competing elements?
   358→- [ ] **Chunking**: Is information presented in digestible groups (≤4 items per group)?
   359→- [ ] **Grouping**: Are related items visually grouped together (proximity, borders, shared background)?
   360→- [ ] **Visual hierarchy**: Is it immediately clear what's most important on the screen?
   361→- [ ] **One thing at a time**: Can the user focus on a single decision before moving to the next?
   362→- [ ] **Minimal choices**: Are decisions simplified (≤4 visible options at any decision point)?
   363→- [ ] **Working memory**: Does the user need to remember information from a previous screen to act on the current one?
   364→- [ ] **Progressive disclosure**: Is complexity revealed only when the user needs it?
   365→
   366→**Scoring**: Count the failed items. 0–1 failures = low cognitive load (good). 2–3 = moderate (address soon). 4+ = high cognitive load (critical fix needed).
   367→
   368→---
   369→
   370→#### The Working Memory Rule
   371→
   372→**Humans can hold ≤4 items in working memory at once** (Miller's Law revised by Cowan, 2001).
   373→
   374→At any decision point, count the number of distinct options, actions, or pieces of information a user must simultaneously consider:
   375→- **≤4 items**: Within working memory limits, manageable
   376→- **5–7 items**: Pushing the boundary; consider grouping or progressive disclosure
   377→- **8+ items**: Overloaded; users will skip, misclick, or abandon
   378→
   379→**Practical applications**:
   380→- Action buttons: 1 primary, 1–2 secondary, group the rest in a menu
   381→- Navigation menus: ≤5 top-level items (group the rest under clear categories)
   382→- Long-form articles: one reading path; gather related links into a single block at the end instead of scattering them mid-flow
   383→- Documentation sidebars: ≤4 sibling choices visible per level before grouping kicks in
   384→- Portfolio and gallery indexes: one decision per screen (which piece to open), not filter, sort, and tag controls all at once
   385→
   386→---
   387→
   388→#### Common Cognitive Load Violations
   389→
   390→##### 1. The Wall of Options
   391→**Problem**: Presenting 10+ choices at once with no hierarchy.
   392→**Fix**: Group into categories, highlight recommended, use progressive disclosure.
   393→
   394→##### 2. The Memory Bridge
   395→**Problem**: User must remember info from step 1 to complete step 3.
   396→**Fix**: Keep relevant context visible, or repeat it where it's needed.
   397→
   398→##### 3. The Hidden Navigation
   399→**Problem**: User must build a mental map of where things are.
   400→**Fix**: Always show current location (breadcrumbs, active states, progress indicators).
   401→
   402→##### 4. The Jargon Barrier
   403→**Problem**: Technical or domain language forces translation effort.
   404→**Fix**: Use plain language. If domain terms are unavoidable, define them inline.
   405→
   406→##### 5. The Visual Noise Floor
   407→**Problem**: Every element has the same visual weight; nothing stands out.
   408→**Fix**: Establish clear hierarchy: one primary element, 2–3 secondary, everything else muted.
   409→
   410→##### 6. The Inconsistent Pattern
   411→**Problem**: Similar actions work differently in different places.
   412→**Fix**: Standardize interaction patterns. Same type of action = same type of UI.
   413→
   414→##### 7. The Multi-Task Demand
   415→**Problem**: Interface requires processing multiple simultaneous inputs (reading + deciding + navigating).
   416→**Fix**: Sequence the steps. Let the user do one thing at a time.
   417→
   418→##### 8. The Context Switch
   419→**Problem**: User must jump between screens/tabs/modals to gather info for a single decision.
   420→**Fix**: Co-locate the information needed for each decision. Reduce back-and-forth.

   424→### Heuristics Scoring Guide
   425→
   426→Score each of Nielsen's 10 Usability Heuristics on a 0–4 scale. Be honest: a 4 means genuinely excellent, not "good enough."
   427→
   428→#### Nielsen's 10 Heuristics
   429→
   430→##### 1. Visibility of System Status
   431→
   432→Keep users informed about what's happening through timely, appropriate feedback.
   433→
   434→**Check for**:
   435→- Loading indicators during async operations
   436→- Confirmation of user actions (save, submit, delete)
   437→- Progress indicators for multi-step processes
   438→- Current location in navigation (breadcrumbs, active states)
   439→- Form validation feedback (inline, not just on submit)
   440→
   441→**Scoring**:
   442→| Score | Criteria |
   443→|-------|----------|
   444→| 0 | No feedback; user is guessing what happened |
   445→| 1 | Rare feedback; most actions produce no visible response |
   446→| 2 | Partial; some states communicated, major gaps remain |
   447→| 3 | Good; most operations give clear feedback, minor gaps |
   448→| 4 | Excellent; every action confirms, progress is always visible |
   449→
   450→##### 2. Match Between System and Real World
   451→
   452→Speak the user's language. Follow real-world conventions. Information appears in natural, logical order.
   453→
   454→**Check for**:
   455→- Familiar terminology (no unexplained jargon)
   456→- Logical information order matching user expectations
   457→- Recognizable icons and metaphors
   458→- Domain-appropriate language for the target audience
   459→- Natural reading flow (left-to-right, top-to-bottom priority)
   460→
   461→**Scoring**:
   462→| Score | Criteria |
   463→|-------|----------|
   464→| 0 | Pure tech jargon, alien to users |
   465→| 1 | Mostly confusing; requires domain expertise to navigate |
   466→| 2 | Mixed; some plain language, some jargon leaks through |
   467→| 3 | Mostly natural; occasional term needs context |
   468→| 4 | Speaks the user's language fluently throughout |
   469→
   470→##### 3. User Control and Freedom
   471→
   472→Users need a clear "emergency exit" from unwanted states without extended dialogue.
   473→
   474→**Check for**:
   475→- Undo/redo functionality
   476→- Cancel buttons on forms and modals
   477→- Clear navigation back to safety (home, previous)
   478→- Easy way to clear filters, search, selections
   479→- Escape from long or multi-step processes
   480→
   481→**Scoring**:
   482→| Score | Criteria |
   483→|-------|----------|
   484→| 0 | Users get trapped; no way out without refreshing |
   485→| 1 | Difficult exits; must find obscure paths to escape |
   486→| 2 | Some exits; main flows have escape, edge cases don't |
   487→| 3 | Good control; users can exit and undo most actions |
   488→| 4 | Full control; undo, cancel, back, and escape everywhere |
   489→
   490→##### 4. Consistency and Standards
   491→
   492→Users shouldn't wonder whether different words, situations, or actions mean the same thing.
   493→
   494→**Check for**:
   495→- Consistent terminology throughout the interface
   496→- Same actions produce same results everywhere
   497→- Platform conventions followed (standard UI patterns)
   498→- Visual consistency (colors, typography, spacing, components)
   499→- Consistent interaction patterns (same gesture = same behavior)
   500→
   501→**Scoring**:
   502→| Score | Criteria |
   503→|-------|----------|
   504→| 0 | Inconsistent everywhere; feels like different products stitched together |
   505→| 1 | Many inconsistencies; similar things look/behave differently |
   506→| 2 | Partially consistent; main flows match, details diverge |
   507→| 3 | Mostly consistent; occasional deviation, nothing confusing |
   508→| 4 | Fully consistent; cohesive system, predictable behavior |
   509→
   510→##### 5. Error Prevention
   511→
   512→Better than good error messages is a design that prevents problems in the first place.
   513→
   514→**Check for**:
   515→- Confirmation before destructive actions (delete, overwrite)
   516→- Constraints preventing invalid input (date pickers, dropdowns)
   517→- Smart defaults that reduce errors
   518→- Clear labels that prevent misunderstanding
   519→- Autosave and draft recovery
   520→
   521→**Scoring**:
   522→| Score | Criteria |
   523→|-------|----------|
   524→| 0 | Errors easy to make; no guardrails anywhere |
   525→| 1 | Few safeguards; some inputs validated, most aren't |
   526→| 2 | Partial prevention; common errors caught, edge cases slip |
   527→| 3 | Good prevention; most error paths blocked proactively |
   528→| 4 | Excellent; errors nearly impossible through smart constraints |
   529→
   530→##### 6. Recognition Rather Than Recall
   531→
   532→Minimize memory load. Make objects, actions, and options visible or easily retrievable.
   533→
   534→**Check for**:
   535→- Visible options (not buried in hidden menus)
   536→- Contextual help when needed (tooltips, inline hints)
   537→- Recent items and history
   538→- Autocomplete and suggestions
   539→- Labels on icons (not icon-only navigation)
   540→
   541→**Scoring**:
   542→| Score | Criteria |
   543→|-------|----------|
   544→| 0 | Heavy memorization; users must remember paths and commands |
   545→| 1 | Mostly recall; many hidden features, few visible cues |
   546→| 2 | Some aids; main actions visible, secondary features hidden |
   547→| 3 | Good recognition; most things discoverable, few memory demands |
   548→| 4 | Everything discoverable; users never need to memorize |
   549→
   550→##### 7. Flexibility and Efficiency of Use
   551→
   552→Accelerators, invisible to novices, speed up expert interaction.
   553→
   554→**Check for**:
   555→- Keyboard shortcuts for common actions
   556→- Customizable interface elements
   557→- Recent items and favorites
   558→- Bulk/batch actions
   559→- Power user features that don't complicate the basics
   560→
   561→**Scoring**:
   562→| Score | Criteria |
   563→|-------|----------|
   564→| 0 | One rigid path; no shortcuts or alternatives |
   565→| 1 | Limited flexibility; few alternatives to the main path |
   566→| 2 | Some shortcuts; basic keyboard support, limited bulk actions |
   567→| 3 | Good accelerators; keyboard nav, some customization |
   568→| 4 | Highly flexible; multiple paths, power features, customizable |
   569→
   570→##### 8. Aesthetic and Minimalist Design
   571→
   572→Interfaces should not contain irrelevant or rarely needed information. Every element should serve a purpose.
   573→
   574→**Check for**:
   575→- Only necessary information visible at each step
   576→- Clear visual hierarchy directing attention
   577→- Purposeful use of color and emphasis
   578→- No decorative clutter competing for attention
   579→- Focused, uncluttered layouts
   580→
   581→**Scoring**:
   582→| Score | Criteria |
   583→|-------|----------|
   584→| 0 | Overwhelming; everything competes for attention equally |
   585→| 1 | Cluttered; too much noise, hard to find what matters |
   586→| 2 | Some clutter; main content clear, periphery noisy |
   587→| 3 | Mostly clean; focused design, minor visual noise |
   588→| 4 | Perfectly minimal; every element earns its pixel |
   589→
   590→##### 9. Help Users Recognize, Diagnose, and Recover from Errors
   591→
   592→Error messages should use plain language, precisely indicate the problem, and constructively suggest a solution.
   593→
   594→**Check for**:
   595→- Plain language error messages (no error codes for users)
   596→- Specific problem identification ("Email is missing @" not "Invalid input")
   597→- Actionable recovery suggestions
   598→- Errors displayed near the source of the problem
   599→- Non-blocking error handling (don't wipe the form)
   600→
   601→**Scoring**:
   602→| Score | Criteria |
   603→|-------|----------|
   604→| 0 | Cryptic errors; codes, jargon, or no message at all |
   605→| 1 | Vague errors; "Something went wrong" with no guidance |
   606→| 2 | Clear but unhelpful; names the problem but not the fix |
   607→| 3 | Clear with suggestions; identifies problem and offers next steps |
   608→| 4 | Perfect recovery; pinpoints issue, suggests fix, preserves user work |
   609→
   610→##### 10. Help and Documentation
   611→
   612→Even if the system is usable without docs, help should be easy to find, task-focused, and concise.
   613→
   614→**Check for**:
   615→- Searchable help or documentation
   616→- Contextual help (tooltips, inline hints, guided tours)
   617→- Task-focused organization (not feature-organized)
   618→- Concise, scannable content
   619→- Easy access without leaving current context
   620→
   621→**Scoring**:
   622→| Score | Criteria |
   623→|-------|----------|
   624→| 0 | No help available anywhere |
   625→| 1 | Help exists but hard to find or irrelevant |
   626→| 2 | Basic help; FAQ or docs exist, not contextual |
   627→| 3 | Good documentation; searchable, mostly task-focused |
   628→| 4 | Excellent contextual help; right info at the right moment |
   629→
   630→---
   631→
   632→#### Score Summary
   633→
   634→**Total possible**: 40 points (10 heuristics × 4 max)
   635→
   636→| Score Range | Rating | What It Means |
   637→|-------------|--------|---------------|
   638→| 36–40 | Excellent | Minor polish only; ship it |
   639→| 28–35 | Good | Address weak areas, solid foundation |
   640→| 20–27 | Acceptable | Significant improvements needed before users are happy |
   641→| 12–19 | Poor | Major UX overhaul required; core experience broken |
   642→| 0–11 | Critical | Redesign needed; unusable in current state |
   643→
   644→When heuristics were scored `n/a`, the maximum is lower than 40; read the band off the percentage instead of the raw number (90%+ Excellent, 70%+ Good, 50%+ Acceptable, 30%+ Poor, below that Critical). 24/32 is 75%, so Good.

   648→#### Issue Severity (P0–P3)
   649→
   650→Tag each individual issue found during scoring with a priority level:
   651→
   652→| Priority | Name | Description | Action |
   653→|----------|------|-------------|--------|
   654→| **P0** | Blocking | Prevents task completion entirely | Fix immediately; this is a showstopper |
   655→| **P1** | Major | Causes significant difficulty or confusion | Fix before release |
   656→| **P2** | Minor | Annoyance, but workaround exists | Fix in next pass |
   657→| **P3** | Polish | Nice-to-fix, no real user impact | Fix if time permits |
   658→
   659→**Tip**: If you're unsure between two levels, ask: "Would a user contact support about this?" If yes, it's at least P1.

   663→### Persona-Based Design Testing
   664→
   665→Test the interface through the eyes of 5 distinct user archetypes. Each persona exposes different failure modes that a single "design director" perspective would miss.
   666→
   667→**How to use**: Select 2–3 personas most relevant to the interface being critiqued. Walk through the primary user action as each persona. Report specific red flags, not generic concerns.
   668→
   669→---
   670→
   671→#### 1. Impatient Power User: "Alex"
   672→
   673→
   674→**Profile**: Expert with similar products. Expects efficiency, hates hand-holding. Will find shortcuts or leave.
   675→
   676→**Behaviors**:
   677→- Skips all onboarding and instructions
   678→- Looks for keyboard shortcuts immediately
   679→- Tries to bulk-select, batch-edit, and automate
   680→- Gets frustrated by required steps that feel unnecessary
   681→- Abandons if anything feels slow or patronizing
   682→
   683→**Test Questions**:
   684→- Can Alex complete the core task in under 60 seconds?
   685→- Are there keyboard shortcuts for common actions?
   686→- Can onboarding be skipped entirely?
   687→- Do modals have keyboard dismiss (Esc)?
   688→- Is there a "power user" path (shortcuts, bulk actions)?
   689→
   690→**Red Flags** (report these specifically):
   691→- Forced tutorials or unskippable onboarding
   692→- No keyboard navigation for primary actions
   693→- Slow animations that can't be skipped
   694→- One-item-at-a-time workflows where batch would be natural
   695→- Redundant confirmation steps for low-risk actions
   696→
   697→---
   698→
   699→#### 2. Confused First-Timer: "Jordan"
   700→
   701→**Profile**: Never used this type of product. Needs guidance at every step. Will abandon rather than figure it out.
   702→
   703→**Behaviors**:
   704→- Reads all instructions carefully
   705→- Hesitates before clicking anything unfamiliar
   706→- Looks for help or support constantly
   707→- Misunderstands jargon and abbreviations
   708→- Takes the most literal interpretation of any label
   709→
   710→**Test Questions**:
   711→- Is the first action obviously clear within 5 seconds?
   712→- Are all icons labeled with text?
   713→- Is there contextual help at decision points?
   714→- Does terminology assume prior knowledge?
   715→- Is there a clear "back" or "undo" at every step?
   716→
   717→**Red Flags** (report these specifically):
   718→- Icon-only navigation with no labels
   719→- Technical jargon without explanation
   720→- No visible help option or guidance
   721→- Ambiguous next steps after completing an action
   722→- No confirmation that an action succeeded
   723→
   724→---
   725→
   726→#### 3. Accessibility-Dependent User: "Sam"
   727→
   728→**Profile**: Uses screen reader (VoiceOver/NVDA), keyboard-only navigation. May have low vision, motor impairment, or cognitive differences.
   729→
   730→**Behaviors**:
   731→- Tabs through the interface linearly
   732→- Relies on ARIA labels and heading structure
   733→- Cannot see hover states or visual-only indicators
   734→- Needs adequate color contrast (4.5:1 minimum)
   735→- May use browser zoom up to 200%
   736→
   737→**Test Questions**:
   738→- Can the entire primary flow be completed keyboard-only?
   739→- Are all interactive elements focusable with visible focus indicators?
   740→- Do images have meaningful alt text?
   741→- Is color contrast WCAG AA compliant (4.5:1 for text)?
   742→- Does the screen reader announce state changes (loading, success, errors)?
   743→
   744→**Red Flags** (report these specifically):
   745→- Click-only interactions with no keyboard alternative
   746→- Missing or invisible focus indicators
   747→- Meaning conveyed by color alone (red = error, green = success)
   748→- Unlabeled form fields or buttons
   749→- Time-limited actions without extension option
   750→- Custom components that break screen reader flow
   751→
   752→---
   753→
   754→#### 4. Deliberate Stress Tester: "Riley"
   755→
   756→**Profile**: Methodical user who pushes interfaces beyond the happy path. Tests edge cases, tries unexpected inputs, and probes for gaps in the experience.
   757→
   758→**Behaviors**:
   759→- Tests edge cases intentionally (empty states, long strings, special characters)
   760→- Submits forms with unexpected data (emoji, RTL text, very long values)
   761→- Tries to break workflows by navigating backwards, refreshing mid-flow, or opening in multiple tabs
   762→- Looks for inconsistencies between what the UI promises and what actually happens
   763→- Documents problems methodically
   764→
   765→**Test Questions**:
   766→- What happens at the edges (0 items, 1000 items, very long text)?
   767→- Do error states recover gracefully or leave the UI in a broken state?
   768→- What happens on refresh mid-workflow? Is state preserved?
   769→- Are there features that appear to work but produce broken results?
   770→- How does the UI handle unexpected input (emoji, special chars, paste from Excel)?
   771→
   772→**Red Flags** (report these specifically):
   773→- Features that appear to work but silently fail or produce wrong results
   774→- Error handling that exposes technical details or leaves UI in a broken state
   775→- Empty states that show nothing useful ("No results" with no guidance)
   776→- Workflows that lose user data on refresh or navigation
   777→- Inconsistent behavior between similar interactions in different parts of the UI
   778→

   780→
   781→#### 5. Distracted Mobile User: "Casey"
   782→
   783→**Profile**: Using phone one-handed on the go. Frequently interrupted. Possibly on a slow connection.
   784→
   785→**Behaviors**:
   786→- Uses thumb only; prefers bottom-of-screen actions
   787→- Gets interrupted mid-flow and returns later
   788→- Switches between apps frequently
   789→- Has limited attention span and low patience
   790→- Types as little as possible, prefers taps and selections
   791→
   792→**Test Questions**:
   793→- Are primary actions in the thumb zone (bottom half of screen)?
   794→- Is state preserved if the user leaves and returns?
   795→- Does it work on slow connections (3G)?
   796→- Can forms use autocomplete and smart defaults?
   797→- Are touch targets at least 44×44pt?
   798→
   799→**Red Flags** (report these specifically):
   800→- Important actions positioned at the top of the screen (unreachable by thumb)
   801→- No state persistence; progress lost on tab switch or interruption
   802→- Large text inputs required where selection would work
   803→- Heavy assets loading on every page (no lazy loading)
   804→- Tiny tap targets or targets too close together
